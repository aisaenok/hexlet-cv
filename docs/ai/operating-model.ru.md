# Операционная модель использования ИИ

## Цель
Этот документ фиксирует, как использовать ИИ в проекте `hexlet-cv`, чтобы он:
- ускорял инженерную работу
- не расширял scope изменений неявно
- не ломал архитектурные ограничения
- не нарушал проектные соглашения
- оставался проверяемым и удобным для ревью

ИИ рассматривается как инженерный ассистент, а не как автономный разработчик.

---

## Основные роли ИИ в проекте

### 1. Explain
Используем ИИ, чтобы:
- объяснять код
- объяснять поток данных
- объяснять flow маршрутизации и страниц
- объяснять причины rerender/remount
- объяснять типизацию и архитектурные решения

### 2. Navigate
Используем ИИ, чтобы:
- находить нужные файлы
- строить карту зависимостей между модулями
- искать точки входа и точки расширения
- находить дублирование логики
- отслеживать связи page/layout/props

### 3. Review
Используем ИИ, чтобы:
- ревьюить diff
- находить архитектурные риски
- проверять нарушения проектных соглашений
- находить лишние абстракции и посторонние изменения

### 4. Generate
Используем ИИ, чтобы:
- генерировать локальный boilerplate
- генерировать тесты
- генерировать небольшие typed utilities
- генерировать черновики документации

### 5. Assist in scoped tasks
Используем ИИ в многошаговых задачах только если:
- явно определена цель
- перечислены allowed files
- перечислены forbidden zones
- зафиксированы invariants
- зафиксированы acceptance criteria
- результат можно проверить

---

## Режимы работы ИИ

### 1. Read-only analysis
Разрешено:
- анализировать код
- предлагать гипотезы
- предлагать варианты решения
- объяснять поведение системы
- выделять риски и trade-offs

Запрещено:
- сразу переходить к широким переписываниям
- предлагать крупную реструктуризацию без запроса
- делать выводы без явных допущений

### 2. Guided write
Разрешено:
- вносить локальные изменения в явно заданном scope
- исправлять баг в согласованных файлах
- делать небольшой безопасный рефакторинг
- добавлять тесты или документацию

Обязательный процесс:
1. анализ
2. план
3. локальное изменение
4. diff review
5. проверка результата

### 3. Restricted generation
Разрешено:
- генерировать types / DTO / utilities / test scaffolding
- генерировать небольшие UI-обвязки
- генерировать черновики документации

Запрещено:
- вводить новые архитектурные абстракции без запроса
- самостоятельно переписывать существующие flow
- менять несколько слоев сразу без согласования

---

## Разрешенные сценарии
- explain code
- repo navigation
- local bug analysis
- генерация гипотез для дебага
- генерация тестов
- локальный рефакторинг с явным file scope
- черновики документации
- diff review
- поиск дублирующейся логики
- генерация небольших typed utilities

---

## Ограниченные сценарии
Следующие задачи должны оставаться в read-only режиме, если нет отдельного согласования:
- сквозной рефакторинг
- изменения routing architecture
- изменения auth flow
- широкая реструктуризация FSD
- глобальные переписывания i18n
- redesign shared abstractions
- изменения Inertia page/props contract
- изменения layout architecture
- массовые переименования между модулями
- изменения, затрагивающие MSW contract или предположения об интеграции с backend

---

## Чувствительные зоны в `hexlet-cv`
К зонам повышенного риска относятся:
- Inertia page contract и shape page props
- route definitions и locale-aware routing
- sign-in и sign-up flows
- auth redirects и проверки protected routes
- поведение layout, особенно если оно зависит от server/shared props
- consumers, использующие `usePage().props`
- границы слоев FSD и решения по размещению файлов
- MSW handlers и их соответствие backend behavior
- структура i18n keys и логика UI, зависящая от переводов
- shared UI/app providers

Для этих зон по умолчанию разрешен только такой результат:
- анализ
- генерация гипотез
- план изменений

Write-изменения в этих зонах должны быть минимальными и явно обоснованными.

---

## Правила перед write mode
Перед любым изменением кода нужно определить:
1. Goal
2. Почему задача локальная, а не сквозная
3. Allowed files
4. Forbidden files или зоны
5. Invariants, которые должны сохраниться
6. Acceptance criteria
7. Способ проверки
8. Что считается лишним изменением

---

## Обязательный порядок работы
Для любой нетривиальной задачи используем такой порядок:
1. Сначала запросить анализ
2. Получить гипотезы или варианты решения
3. Выбрать минимальный безопасный подход
4. Зафиксировать scope
5. Внести изменения
6. Провести diff review
7. Проверить через tests / typecheck / manual scenario
8. Зафиксировать выводы

---

## Правила для багов и нестабильного поведения
Если задача связана с багом, нельзя сразу запрашивать фикс.

Сначала нужно:
- собрать симптомы
- описать expected vs actual behavior
- дать минимальный релевантный контекст
- запросить гипотезы
- определить наиболее вероятную root cause
- только потом переходить к реализации

---

## Запрещенные действия без явного разрешения
ИИ не должен без явного запроса:
- переносить файлы между слоями FSD
- менять публичные интерфейсы модулей
- менять shape маршрутов
- массово переименовывать translation keys
- менять shape server / Inertia props
- вводить shared abstractions “на будущее”
- трогать unrelated files
- расширять scope задачи из-за того, что “так будет чище”
- переписывать working code без доказанной необходимости

---

## Минимальный контракт AI-задачи
Каждая write-задача должна включать:

### Goal
Что должно измениться

### Context
Краткий контекст задачи

### Allowed files
Какие файлы можно менять

### Forbidden zones
Какие файлы / слои / flow менять нельзя

### Invariants
Что должно остаться неизменным

### Acceptance criteria
Как оценивается успешность решения

### Verification
Как проверяется результат:
- typecheck
- tests
- manual scenario
- diff review

---

## Definition of done для AI-задачи
AI-assisted задача считается завершенной, только если:
- изменен только согласованный scope
- решение можно объяснить
- нет лишних абстракций
- соблюдены проектные соглашения
- задача не расширилась неявно
- есть проверка результата
- invariants сохранены
- diff локальный и читаемый
- результат можно защитить на code review

---

## Главный принцип
ИИ должен ускорять локальную инженерную работу.

ИИ не должен автоматически принимать архитектурные решения и не должен расширять scope без явного согласования.
