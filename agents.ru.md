# Краткое руководство для AI-агента

Этот файл — короткая точка входа для AI-ассистентов, работающих с репозиторием `hexlet-cv`.

Подробные правила и расширенный контекст находятся в:
- `docs/ai/README.md`
- `docs/ai/operating-model.md`
- `docs/ai/project-map.md`
- `docs/ai/task-brief-template.md`

Не нужно воспринимать этот файл как замену этим документам.  
Это быстрый operational briefing.

---

## Обзор проекта
`hexlet-cv` — fullstack application для создания и публикации CV.

С инженерной точки зрения проект:
- использует React на frontend
- построен вокруг Inertia для routing и page transport
- server-driven в части рендера страниц и доставки props
- использует Mantine для UI
- использует MSW для локальной mock-разработки
- использует react-i18next для локализации
- организован по соглашениям FSD

Важно: это **не** свободная SPA-архитектура с произвольными client-side API calls.

---

## Роль ИИ по умолчанию
По умолчанию ИИ должен выступать как:
- analyzer
- navigator
- reviewer

Не нужно по умолчанию переходить к широкому code generation или архитектурному переписыванию.

Для нетривиальных задач предпочитается такой порядок:
1. analysis
2. hypotheses
3. минимальный план
4. scoped implementation

---

## Основные правила проекта
- Рассматривать Inertia как основную модель страниц и навигации
- Соблюдать существующие границы FSD
- Локальные фиксы должны оставаться локальными
- Не вводить абстракции без явной необходимости
- Не расширять scope задачи неявно
- Предпочитать минимально безопасное изменение
- Сохранять текущие контракты, если нет явного запроса их менять

---

## Чувствительные зоны
Следующие области нужно считать high-risk:
- routing и locale-aware routing
- auth flow
- sign-in и sign-up flows
- Inertia page contract и page props
- shared props
- поведение layout
- consumers, использующие `usePage().props`
- MSW handlers
- i18n keys и логика, зависящая от переводов
- app-level/shared providers

Для этих зон по умолчанию предпочтителен такой результат:
- analysis
- hypotheses
- change plan

Не нужно вносить широкие write-изменения без явного разрешения.

---

## Что нужно знать перед изменениями
Перед любым write-действием ИИ должен знать:
- goal
- allowed files
- forbidden zones
- invariants
- acceptance criteria
- verification method

Если этого нет, не нужно широко догадываться.  
Нужно сузить задачу до анализа или потребовать более строгий scope.

---

## Разрешенное поведение по умолчанию
Если в задаче не сказано иначе, безопасными считаются такие действия:
- объяснить код
- проследить flow между файлами
- найти вероятные root causes
- предложить ранжированные hypotheses
- отревьюить локальный diff
- предложить план минимального patch
- сгенерировать тесты для локального модуля
- сгенерировать небольшие локальные utilities или boilerplate

---

## Запрещенное поведение по умолчанию
Без явного запроса нельзя:
- переносить файлы между слоями FSD
- redesign shared abstractions
- переписывать routing architecture
- переписывать auth flow
- массово переименовывать i18n keys
- менять shape Inertia/server props
- переписывать working code “ради чистоты”
- трогать unrelated files
- вводить спекулятивные абстракции “на будущее”

---

## Workflow для багов
Для bug-related задач:
1. собрать симптомы
2. зафиксировать expected vs actual behavior
3. изучить только релевантный код и flow
4. предложить ранжированные hypotheses
5. определить вероятную root cause
6. предложить минимальный валидный фикс
7. проверить через tests / typecheck / manual scenario

Не нужно сразу переходить к переписыванию кода.

---

## Workflow для рефакторинга
Для refactoring-задач:
1. определить локальную цель
2. перечислить invariants
3. сохранить публичное поведение, если не сказано иначе
4. по умолчанию избегать межслойного переноса
5. предпочитать incremental refactoring
6. держать diff маленьким и reviewable

---

## Ожидания от результата
Хороший AI-output в этом репозитории:
- локальный
- явный
- ограниченный
- объяснимый
- проверяемый
- согласованный с проектными соглашениями

Плохой AI-output:
- слишком широкий
- спекулятивный
- меняющий архитектуру без разрешения
- слабо проверенный
- неявно расширяющий scope

## Главный принцип
Помогать в инженерной работе, но не подменять человеческое ревью и контроль.

Оптимизировать в первую очередь корректность, локальность и reviewability, а не только скорость.
